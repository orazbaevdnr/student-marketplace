# Student Marketplace: backend

Java 21, Spring Boot 3.3, PostgreSQL. Built from the Task 9 database plan.

> **Status: built and tested.** `mvn verify` → BUILD SUCCESS, 22 tests
> (unit, integration and the full `/api/client` contract on H2 with all Flyway migrations).

```bash

mvn spring-boot:run -Dspring-boot.run.profiles=dev

# 2. Real setup (PostgreSQL + daily DB backup)
```

## Architecture

Layered, one package per business area (feature packages), so a change to "listings" stays inside `listing/`.

```
controller  ->  service (@Transactional, business rules)  ->  repository (Spring Data JPA)  ->  PostgreSQL
   DTO records in/out                   entities never leave the service layer
```

| Package | Task 9 part |
|---|---|
| `user`, `auth`, `security` | USERS table, registration, login, JWT, access rules |
| `category` | CATEGORIES table (cached list, administrator edits) |
| `listing` | LISTINGS table, the main action "seller publishes a listing", search |
| `photo` | LISTING_PHOTOS table, file storage |
| `purchase` | PURCHASES table, the buy transaction |
| `stale`, `admin` | SQL report "stale listings", reminders and hiding, administrator tools |
| `db/migration` | Flyway: the 5 tables, constraints and indexes |

## What from the project is covered, and where

| From the project | Implementation |
|---|---|
| 5 tables, primary and foreign keys, relationships | `V1__create_schema.sql` and the entities |
| Main action: seller publishes a listing | `POST /api/listings`, then `POST /api/listings/{id}/photos` |
| Listing ID `L-101`, generated by the system, unique | DB sequence `listing_id_seq`, primary key |
| Problem "L-### allows only 999 listings" | The number part just grows: `L-999`, `L-1000`, ... |
| Price: whole number, greater than 0 | `@Min(1)` on the request, `CHECK (price_kzt > 0)` in the DB, `12.5` and `"12 000 tg"` are rejected |
| Status Available / Reserved / Sold | `ListingStatus`, `CHECK` in the DB. `HIDDEN` was added for the 37-day rule |
| Problem "Sold and Available at once" | `PurchaseService.buy`: one transaction, row lock, `UNIQUE (listing_id)` in PURCHASES |
| Buyers read only Available listings | `ListingService.search` |
| Seller edits only own listings | `ListingService.ownedAndChangeable`, 403 otherwise |
| Administrator has full access, only the administrator sees e-mails | `/api/admin/**` requires `ROLE_ADMIN`; e-mails are only in `/api/users/me` and admin endpoints |
| No orphan records | foreign keys, `ON DELETE CASCADE` for photos, users and purchased listings are never deleted |
| Photos: many per listing, path in the DB | `listing_photos`, files in `PHOTO_DIR`, max 5 per listing, type checked by file header |
| SQL: Available listings older than 30 days | `GET /api/admin/reports/stale-listings?days=30` |
| Decision: remind at 30 days, hide at 37 days | `StaleListingService`, nightly at 03:00, or `POST /api/admin/jobs/stale-listings` |
| Seller confirms "still for sale" | `POST /api/listings/{id}/confirm` (any edit also confirms) |
| Problem "no automatic backup" | `db-backup` service in `docker-compose.yml`, `scripts/backup-photos.sh` |
| Price history, data vs information | not stored (also "still to improve" in the plan) |

## Endpoints

| Method and path | Who | What |
|---|---|---|
| `POST /api/auth/register`, `POST /api/auth/login` | anyone | register with a university e-mail, get a JWT |
| `GET /api/users/me` | logged in | own profile |
| `GET /api/categories` | anyone | active categories (cached) |
| `GET /api/listings?q=&categoryId=&minPrice=&maxPrice=&sellerId=&page=&size=&sort=` | logged in | search, Available only |
| `GET /api/listings/mine?status=` | seller | own listings in every status |
| `GET /api/listings/{id}` | logged in | details with photos |
| `POST /api/listings`, `PUT /api/listings/{id}` | seller | publish and edit |
| `PATCH /api/listings/{id}/status` | seller | `AVAILABLE` or `RESERVED` |
| `POST /api/listings/{id}/confirm` | seller | still for sale |
| `DELETE /api/listings/{id}` | seller, admin | only if never purchased |
| `POST/DELETE /api/listings/{id}/photos[/{photoId}]` | seller | upload (multipart field `file`) and remove |
| `GET /api/listings/{id}/photos/{photoId}/content` | anyone | the image |
| `POST /api/listings/{id}/purchase` | buyer | buy, 409 if already sold |
| `GET /api/purchases/mine`, `GET /api/purchases/sales` | logged in | purchases and sales |
| `GET /api/admin/users`, `PATCH /api/admin/users/{id}/active` | admin | list, deactivate and reactivate accounts |
| `GET/POST/PUT /api/admin/categories`, `PATCH .../{id}/active` | admin | manage categories |
| `GET /api/admin/reports/stale-listings`, `/reports/summary`, `/purchases` | admin | information for decisions |
| `POST /api/admin/jobs/stale-listings` | admin | run the nightly job now |

Errors are RFC 7807 JSON (`{"status":409,"detail":"..."}`); validation errors also have an `errors` object per field.

## Why it is built this way

- **Layers and feature packages:** simple to explain and to test; DTO records keep entities and passwords out of JSON.
- **Flyway + `ddl-auto: none`:** the database schema is versioned code, the same as the Task 9 plan. Hibernate never changes it.
- **Constraints in the database *and* in the code:** the code gives friendly errors, the database is the last safety net (price, status, unique purchase).
- **Concurrency:** the buy transaction locks the listing row; `@Version` on listings stops silent overwrites.
- **Performance:** `open-in-view: false`; the search uses an entity graph (seller and category in the same query), main photos are loaded with one extra query per page (no N+1), batch fetching is on, indexes match the filters (status, category, seller, price, last_updated), page size is limited to 50, sort fields are whitelisted, categories and photo files are cached.
- **Stateless JWT:** no session store, easy to scale. Trade-off: a deactivated account's old token still works for reading until it expires (default 60 minutes). Write actions (create listing, buy) check the account in the database, so a banned user cannot publish or buy.

## Connecting the React frontend

`/api/client/**` is the contract the React app uses (slug categories, lowercase condition, `active/sold` status, 1-indexed pages `{items,total,page,pageSize}`, absolute image URLs, favorites, profile fields). Login is JWT only:

1. Backend: `CORS_ORIGINS=http://localhost:5173` (default) and a 32+ character `JWT_SECRET` (the `dev` profile already has one).
2. Frontend `.env`: `VITE_API_BASE_URL=/api/client` (Vite proxies `/api` to `http://localhost:8080`).

`POST /api/client/auth/register` and `POST /api/client/auth/login` return `{token, tokenType, expiresInSeconds, user}`. Send `Authorization: Bearer <token>` on later requests. `GET /api/client/auth/me` restores the session.

Notes:
- Images are sent as `data:image/png|jpeg|webp;base64,...` (max 5 per listing, 5 MB each) and returned as URLs. To keep a picture on update, send its URL back.
- Status values `reserved` and `hidden` exist besides `active` and `sold`. `PATCH .../status` accepts only `sold` (sold outside the app) and `active`.
- The catalog is public; without a token the seller `contact` is hidden. Prices are KZT; an e-mail must be from `ALLOWED_EMAIL_DOMAIN` (default `kbtu.kz`).
- User ids in URLs: `me` or the numeric id.
- Sort `newest` uses creation time, then id; listings created within the same second can swap places.

## Known limits and next steps

- Reminders are written to the log (`LoggingReminderNotifier`). Add an e-mail implementation of `ReminderNotifier` to really send them.
- The nightly job is meant for **one** application instance. With several instances use a lock (ShedLock) or one external scheduler.
- Search uses `LIKE` on title and description. For many thousands of listings switch to PostgreSQL full-text search or trigram indexes.
- No rate limit on login and registration in production? **There is one now**: `LoginRateLimitFilter`
  (default 20 attempts per IP per minute, `AUTH_RATE_LIMIT_PER_MINUTE`) plus Nginx `limit_req` in
  front of the same routes. The state is in memory, so it is per instance.
- Photos are stored on a local disk/volume. For several servers use S3-compatible storage (`PhotoStorage` is the only class to change).
- Not implemented because the plan did not ask for it: payments, chat between users, price history.
- `ALLOWED_EMAIL_DOMAIN` defaults to `kbtu.kz` (assumption). Set it empty to allow any e-mail.
