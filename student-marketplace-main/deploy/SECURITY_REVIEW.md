# Security review

Date: 2026-11-16
Scope: React frontend (`student-marketplace-front/student-marketplace-main`), Spring Boot
backend (`student-marketplace-back/student-marketplace`), and the Docker/Nginx bundle
(`deploy/`).

Method: manual code review of the authentication, authorization, file upload, error handling
and configuration paths; dependency audit with `npm audit`; review of the production container
configuration; `mvn verify` and `npm run build` as an executable check of the described
behaviour. No external penetration test was performed.

### Backend

Spring Boot 3.3.5, `jjwt` 0.12.6, `springdoc-openapi` 2.6.0, Flyway and the PostgreSQL driver,
all managed by the Spring Boot BOM except the two explicit versions above.

No CVE feed scan is part of this review:

- `org.sonatype.ossindex.maven:ossindex-maven-plugin` cannot be used: the service answers
  HTTP 401 without an account;
- `org.owasp:dependency-check-maven` needs the full NVD feed (~421k records) on its first run,
  which takes hours without an NVD API key and was not completed.

**Open action item** — run the scan once with a key, then keep it in CI:

```bash
mvn org.owasp:dependency-check-maven:check -DnvdApiKey=<key> -DfailBuildOnCVSS=7
```

Until then, treat the backend dependency tree as "reviewed by version, not by CVE feed".

## 3. Findings and fixes

### F-1 (High) — Client-side data and authentication

The frontend shipped a mock adapter with `localStorage` persistence, a one-click demo login and
Firebase Auth. That made the browser the source of truth and allowed a session without any
credential check.

Fixed: `src/api/mockAdapter.ts`, `src/api/seed.ts`, `src/auth/firebase.ts`, the demo-login
button and the e-mail verification screens are deleted. The only implementation of `ApiClient`
is `restAdapter.ts`, which talks to `/api/client/**` and attaches `Authorization: Bearer …`.
`localStorage` now holds the JWT and nothing else.

### F-2 (High) — Brute force on the password endpoints

`/api/client/auth/login` and `/register` accepted unlimited attempts.

Fixed in two layers:

- `security/LoginRateLimitFilter` — sliding 60-second window per client IP, default 20
  attempts (`AUTH_RATE_LIMIT_PER_MINUTE`), answers `429` with `Retry-After: 60`. Unit-tested by
  `LoginRateLimitFilterTest` (3 tests: limit reached, per-client isolation, only
  login/register POSTs are limited).
- Nginx `limit_req zone=auth rate=10r/m burst=5` on
  `^/api/(client/)?auth/(login|register)$`.

The filter state is in memory, so it is per backend instance — see §5.

### F-3 (Medium) — Missing browser security headers

Added by Nginx (`deploy/nginx/default.conf` and `https.conf.example`):

`Content-Security-Policy`, `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`,
`Referrer-Policy`, `Permissions-Policy`, `Cross-Origin-Opener-Policy: same-origin`,
`Cross-Origin-Resource-Policy: same-origin`; HSTS in the HTTPS variant.

The CSP is strict because nothing external is loaded any more:

```
default-src 'self'; script-src 'self'; img-src 'self' data: blob:; connect-src 'self';
frame-src 'none'; object-src 'none'; base-uri 'self'; form-action 'self'
```

`script-src 'self'` works because the Vite build emits no inline scripts. `img-src` allows
`data:`/`blob:` for the canvas-based image resize; there is no placeholder service and no CDN.
`connect-src 'self'` is enough because the API is proxied on the same origin.

Spring Security's defaults (`nosniff`, `X-Frame-Options: DENY`, `Cache-Control`) still apply to
the backend responses; the header set that matters for browsers is the one Nginx sends for the
SPA.

### F-4 (Medium) — Production leaked developer endpoints and stack traces

`application-prod.yml` (activated by `SPRING_PROFILES_ACTIVE=prod` in the compose file)
disables Swagger/OpenAPI and `/v3/api-docs`, exposes only `/actuator/health` with
`show-details: never`, and disables message/stacktrace/binding-error output.

### F-5 (Medium) — Deployment exposed the backend and database directly

The compose file publishes only the frontend (80/443). PostgreSQL and the backend are on an
internal Docker network with no published ports. Containers run with `no-new-privileges`; the
backend image creates and uses a non-root `marketplace` user.

### F-6 (Low) — No container health checks / fragile startup order

The backend image has a `HEALTHCHECK` (bash `/dev/tcp` on port 8080, because the JRE image
ships neither curl nor wget) and the frontend has one on `/healthz`. Compose waits for `db`
and `backend` to be healthy before starting dependants.

### F-7 (Low) — Secrets could be committed accidentally

`deploy/.env.prod`, `deploy/backups/` and `deploy/nginx/certs/` are ignored. The example file
contains placeholders only. `deploy/scripts/generate-secrets.ps1` generates URL-safe random
values and refuses to overwrite an existing file.

### F-8 (Low) — Default Spring Security user was created at startup

`UserDetailsServiceAutoConfiguration` created an in-memory `user` with a random password and
logged it at every start. The application does not use form login, so the account was not
reachable, but it was unnecessary surface and log noise. Excluded in `MarketplaceApplication`.

## 4. Controls verified as correct

- **Password storage**: BCrypt (`BCryptPasswordEncoder`); an unknown e-mail is compared against
  a dummy hash so the response time does not reveal whether an account exists, and the error
  message is generic.
- **JWT**: HMAC-SHA256 over a secret that must be at least 32 bytes (the application refuses to
  start otherwise), `sub` = user id, `email` and `role` claims, `iat`/`exp` validated on every
  request by `JwtAuthFilter`; `401` on a bad or expired token. Tokens are stateless — there is
  no refresh token, so `JWT_TTL_MINUTES` bounds a stolen token's lifetime.
- **Registration policy**: optional `ALLOWED_EMAIL_DOMAIN` (default `kbtu.kz`) enforced on the
  server. `email_verified` is stored as `true`; there is no verification flow, and no
  authorization decision depends on it.
- **Authorization / IDOR**: update, delete, photo changes, status changes and profile changes
  check ownership in the service layer (`ForbiddenException`), not only in the UI.
- **Admin area**: both the `/api/admin/**` URL rule and `@PreAuthorize("hasRole('ADMIN')")`.
- **File uploads**: magic-byte detection (JPEG/PNG/WebP only), generated UUID file names,
  `root.resolve(...).normalize()` + `startsWith(root)` path-traversal guard, 5 MB per file /
  6 MB per request, max 5 photos per listing.
- **CSRF**: not applicable — stateless bearer tokens, no cookies, no sessions. CSRF protection
  is disabled deliberately and that is safe under these conditions.
- **CORS**: explicit origin allow-list from `CORS_ORIGINS`, limited methods and headers,
  credentials disabled.
- **XSS**: no `dangerouslySetInnerHTML`, `innerHTML`, `eval` or `new Function` in the frontend;
  React escapes user content. The only rendered URLs come from the API or from the user's own
  upload — no third-party image hosts.
- **SQL injection**: all access through Spring Data JPA / derived queries; no string-built SQL.
- **Error handling**: RFC 7807 `ProblemDetail`, no stack traces to clients, upload size
  exceeded handled explicitly.

## 5. Residual risks and recommendations

| Risk | Severity | Recommendation |
|---|---|---|
| TLS is not enabled by default (HTTP config ships first) | High if forgotten | Enable `https.conf.example` before opening the site to users; see DEPLOYMENT.md §4 |
| Rate limiter state is per instance and in memory | Low | Fine for one backend replica; move to Redis/Bucket4j if you scale horizontally |
| Backend dependency CVEs not fully scanned yet | Medium | Run OWASP dependency-check with an NVD API key, or enable Dependabot/Snyk in CI |
| JWT lives in `localStorage` | Medium | Acceptable for this project; an `HttpOnly` cookie + CSRF token would resist XSS-driven token theft better |
| No token revocation / refresh | Low | Rotate `JWT_SECRET` to invalidate all sessions; short TTL limits exposure |
| No malware scan of uploaded images | Low | Magic-byte check + size limits are in place; add ClamAV if the threat model requires it |
| Admin has no MFA | Medium | Use a long generated password and a dedicated admin account |
| Backups are unencrypted at rest | Medium | Encrypt the backup target or the volume; test restores regularly |
| No WAF / DDoS protection | Low | Put Cloudflare or a provider firewall in front if the site is public |
| Logs contain user e-mails | Low | Set a retention policy; do not ship logs to third parties without review |

