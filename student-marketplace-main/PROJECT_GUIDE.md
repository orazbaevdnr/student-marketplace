# Полное руководство по проекту: Student Marketplace (От «А» до «Я»)

Этот документ описывает архитектуру проекта, взаимодействие фронтенда, бэкенда и базы данных, а также содержит **готовое распределение ролей на 5 человек для защиты перед комиссией**.

---

## ЧАСТЬ 1. Как устроен и работает проект (Архитектура «От А до Я»)

### 1. Общая схема системы
```
┌──────────────────────────────────────────────────────────────────┐
│                           ПОЛЬЗОВАТЕЛЬ                           │
│                      (Браузер / Смартфон)                        │
└─────────────────────────────────┬────────────────────────────────┘
                                  │ HTTP / HTTPS
                                  ▼
┌──────────────────────────────────────────────────────────────────┐
│                  ФРОНТЕНД (React 18 + Vite + TS)                 │
│  - Маршрутизация (React Router v7 + ProtectedRoute)              │
│  - Компоненты UI (Tailwind CSS, карточки, модалки, тосты)        │
│  - Состояние и сессия (AuthContext + useFavorites)               │
│  - Единственный слой HTTP: src/api/restAdapter.ts                │
└─────────────────────────────────┬────────────────────────────────┘
                                  │ /api/client/**  +  Bearer JWT
                                  ▼
┌──────────────────────────────────────────────────────────────────┐
│              БЭКЕНД (Java 21 + Spring Boot 3.3)                  │
│  - Spring Security + JWT (BCrypt для паролей)                    │
│  - Контроллеры → сервисы → репозитории (Spring Data JPA)         │
│  - Hibernate 6: сущности, связи, транзакции                      │
│  - Flyway: версионирование схемы (V1–V4)                         │
└─────────────────────────────────┬────────────────────────────────┘
                                  │ JDBC
                                  ▼
┌──────────────────────────────────────────────────────────────────┐
│                     POSTGRESQL 16                                │
│  users, categories, listings, listing_photos, purchases,         │
│  favorites + ограничения, индексы, внешние ключи                 │
└──────────────────────────────────────────────────────────────────┘
```

Ключевая идея: **источник правды — бэкенд и база данных**. Фронтенд не хранит бизнес-данные, не содержит моков и не решает, какие объявления показывать: он только вызывает REST API и отображает ответ.

---

### 2. Как устроен Фронтенд (Frontend)

* **Интерфейс и стили (Tailwind CSS):** адаптивный дизайн Mobile-First от 360px до 4K. На мобильных — нижняя навигация (`BottomNav`), на десктопе — верхний хедер с поиском.
* **Маршрутизация (React Router v7):**
  - Публичная страница: `/login`.
  - Защищённые страницы: `/` (каталог), `/listing/:id`, `/listings/new`, `/listings/:id/edit`, `/my-listings`, `/favorites`, `/profile`.
  - `ProtectedRoute` перенаправляет неавторизованного пользователя на `/login` и запоминает исходный путь, чтобы вернуть его туда после входа.
* **Слой данных (`src/api/`):** интерфейс `ApiClient` и единственная реализация `RestApiClient`, которая обращается к `/api/client/**`, добавляет `Authorization: Bearer <token>` и централизованно обрабатывает `401` (очищает токен и возвращает на логин). Никаких мок-адаптеров и `localStorage`-базы нет.
* **Каталог и поиск:** задержка 300 мс (`useDebounce`), фильтры по категории, состоянию, цене и сортировке синхронизированы с URL, поэтому ссылку с фильтрами можно скопировать и открыть заново.
* **Оптимистичный UI:** «сердечко» избранного загорается мгновенно, а при ошибке запроса состояние откатывается.
* **Обработка картинок:** фото сжимаются в браузере через HTML5 Canvas до 1024px и отправляются на бэкенд как base64 data URL; бэкенд проверяет формат и сохраняет файлы.

---

### 3. Как устроен Бэкенд и База Данных (Backend & Database)

* **Spring Boot 3.3 / Java 21.** Слоистая архитектура, по пакетам на бизнес-область:
  `controller → service (@Transactional) → repository (Spring Data JPA) → PostgreSQL`. Сущности JPA не выходят за пределы сервисного слоя — наружу отдаются DTO-записи.
* **PostgreSQL 16 — единственная база.** Схема описана миграциями Flyway (`src/main/resources/db/migration`):
  - `V1__create_schema.sql` — таблицы `users`, `categories`, `listings`, `listing_photos`, `purchases`, ограничения и индексы;
  - `V2__seed_categories.sql` — стартовые категории;
  - `V3__frontend_support.sql` — slug категорий, состояние товара, профиль, избранное;
  - `V4__drop_firebase.sql` — удаление колонки `firebase_uid`: Firebase в проекте больше не используется.
* **Hibernate** работает с `ddl-auto: none`: схему меняет только Flyway, ORM никогда не трогает структуру таблиц. Это защищает данные при обновлении приложения.
* **Аутентификация:** `POST /api/client/auth/register` и `/login` создают подписанный JWT (`JwtService`, HMAC-SHA256, TTL по умолчанию 60 минут). `JwtAuthFilter` проверяет токен на каждом запросе и кладёт пользователя в `SecurityContext`. Пароли хранятся только как BCrypt-хеши.
* **Правила бизнес-логики на сервере:** цену, состояние, лимит фото, права на редактирование («только свой товар»), статусы `active / reserved / sold / hidden` и правило скрытия объявления через 37 дней проверяет бэкенд — фронтенд лишь отображает результат.
* **Фотографии:** файлы лежат на диске (`PHOTO_DIR`), пути — в `listing_photos`; API возвращает абсолютные URL, которые работают и в dev, и за Nginx.
* **Наблюдаемость и надёжность:** Flyway, `open-in-view: false`, пагинация с ограничением размера страницы, `@Version` на объявлениях, блокировка строки при покупке, ежедневный бэкап БД в docker-compose.

## ЧАСТЬ 3. Быстрая шпаргалка к вопросам преподавателей

1. **Вопрос:** *«Где физически хранятся данные?»*
   - **Ответ:** *«В PostgreSQL 16. В production это контейнер с постоянным volume, в разработке можно поднять H2 в режиме совместимости с PostgreSQL. Структура таблиц создаётся миграциями Flyway, а ORM-сущности Hibernate с ней только сопоставляются.»*
2. **Вопрос:** *«Что произойдёт, если поменять схему базы?»*
   - **Ответ:** *«Добавляется новая миграция Flyway, приложение при старте применяет её и записывает версию в `flyway_schema_history`. Hibernate не меняет схему сам, поэтому случайная потеря данных исключена.»*
3. **Вопрос:** *«Почему на клиенте сжимаются изображения?»*
   - **Ответ:** *«Фото с телефона весит 5–10 МБ. Ресайз до 1024px уменьшает его примерно до 150 КБ: экономится трафик студента и ускоряется каталог, при этом бэкенд всё равно проверяет тип и размер файла.»*
4. **Вопрос:** *«Как защищены пароли и сессии?»*
   - **Ответ:** *«Пароли хранятся только как BCrypt-хеши. Аутентификация stateless: сервер выдаёт подписанный JWT, проверяет подпись и срок жизни на каждом запросе, а на фронтенде токен автоматически очищается при 401. CSRF-атаки не применимы, потому что нет cookie-сессий.»*
5. **Вопрос:** *«Что произойдёт, если база упадёт или пропадёт интернет?»*
   - **Ответ:** *«Фронтенд перехватывает ошибки на уровне `RestApiClient`: каталог показывает Error State с кнопкой Retry, остальные действия — тост с сообщением. Данные не подменяются моками, поэтому пользователь видит честное состояние системы.»*
